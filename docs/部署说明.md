# 部署说明

以下命令均针对新建的独立环境。服务使用固定项目名 `zhenxing_submission` 和独立数据卷，不依赖开发机已有数据库或容器。

## 1. 准备环境

| 项目 | 要求 |
| --- | --- |
| Docker | Docker Engine 或 Docker Desktop，运行 Linux 容器，带 Docker Compose v2 或以上 |
| Compose 特性 | 需要支持 `env_file.required`；如提示配置不支持，请升级 Compose |
| Python | 主机 Python 3.11 或以上，用于生成本地配置和可选的手机网关 |
| 网络 | 首次构建需下载 Docker 镜像、Python/npm依赖及本机 Embedding 权重 |
| 模型API | 有效的 DeepSeek API 密钥、对应模型权限及可用余额 |
| 电脑资源 | 建议4核、16GB内存、20GB可用磁盘。属于演示资源建议，不是容量测评结论 |

电脑服务的运行依赖在容器内安装，主机不必另装 Node.js 或 JDK。只有修改前端或自行构建 APK 时才需要相应工具。

Windows 建议使用 Docker Desktop 的 WSL2 后端。Linux x86_64可按同一Compose流程部署。macOS需使用Docker Desktop；Apple Silicon未完成独立兼容验收，不能只凭Compose语法正常认定所有镜像及ONNX运行时都可用。

检查工具：

```shell
docker version
docker compose version
```

构建 Android 时必须使用英文工程路径，例如 `D:/ZhenxingAgent`。电脑端也建议避免同步盘和过长目录。不要把源码直接解压覆盖正在使用的部署。

## 2. 生成本地配置

打开终端，进入源码根目录下的 `app`。

Windows PowerShell：

```powershell
cd D:\ZhenxingAgent\app
python configure_local.py
notepad .env
```

Linux / macOS：

```sh
cd ~/zhenxing-agent/app
python3 configure_local.py
chmod 600 .env
${EDITOR:-vi} .env
```

把 `ZX_DEEPSEEK_API_KEY=` 的空值改为你自己的密钥。不要把整个`.env`贴到聊天、Issue、截图或公开日志中。配置脚本随机生成数据库口令、客户初始密码后缀及管理员初始口令，已有`.env`会拒绝覆盖。

脚本还在本机生成`app/var/private/首次登录.txt`，里面列出每个初始账户的完整口令，终端只显示文件位置。完成初始化后从该文件取口令登录，无需手工拼接。`.env`和这个私有文件均不应上传GitHub、提交平台或发送给他人。

| 变量 | 默认值或作用 |
| --- | --- |
| `ZX_HTTP_PORT` | 网页与API，默认18965 |
| `ZX_POSTGRES_PORT` | 业务数据库，默认15442 |
| `ZX_KNOWLEDGE_PORT` | 知识数据库，默认15443 |
| `ZX_EMBEDDING_PORT` | 本机Embedding健康与向量接口，默认18193 |
| `ZX_DATABASE_PASSWORD` | 新业务数据库口令 |
| `ZX_KNOWLEDGE_PASSWORD` | 新知识数据库口令 |
| `ZX_INITIAL_CUSTOMER_SUFFIX` | 新环境客户密码后缀，至少12字符 |
| `ZX_INITIAL_ADMIN_PASSWORD` | 新管理员初始口令，至少12字符；配置脚本生成更长的随机口令 |
| `ZX_DEEPSEEK_API_KEY` | 云端主模型凭据，仅由电脑服务端使用 |
| `ZX_SEED_AS_OF` | 可留空，首次初始化默认当天；指定YYYY-MM-DD可固定账单基准日 |
| `ZX_ALLOW_PUBLIC_REGISTRATION` | 默认0，关闭公开注册；需要新账户时通过管理入口处理 |

默认端口均绑定`127.0.0.1`。端口占用时修改`.env`后重新创建本项目容器，不要停止其他项目。管理员口令或后缀只影响首次初始化；修改`.env`不会给已有账户重置密码，也不会修改已创建数据库用户的口令。

## 3. 首次构建与初始化

以下命令都在`app`目录运行，保持同一个项目名：

```shell
docker compose -p zhenxing_submission config --quiet
docker compose -p zhenxing_submission up -d --build
docker compose -p zhenxing_submission ps -a
```

Compose先启动数据库，再运行一次性的`init-data`服务。只有初始化成功、退出码为0，API和业务Worker才启动。因此`init-data`显示`Exited (0)`是正常状态，不需要让它持续运行。其余服务保持运行。

初始化模块为`zhenxing.release_seed`，只接受空的新业务库，完整创建后写入版本标记。再次运行会返回`replayed: true`，不补回已花资金、不恢复用户取消的订阅。非空且没有对应标记的库会拒绝，API和Worker也不会绕过这一步继续启动。

默认账单基准日为首次初始化当天。需要固定日期复现时，在第一次启动前将`.env`里的`ZX_SEED_AS_OF`设置为例如`2026-10-30`。只有初始化前生效，后续不能通过改配置重写已有账本的基准日。

查看初始化结果：

```shell
docker compose -p zhenxing_submission logs --tail=50 init-data
```

首次成功应包含`customer_count: 14`、`cards_per_customer`中借记2张和信用1张、`subscriptions_per_customer: 2`，以及`replayed: false`。已有完整环境重新启动时可以是`replayed: true`。完整数据口径见[样例数据](样例数据.md)。

需要显式重放初始化以检查标记时，可在数据库已健康且当前没有未完成初始化的情况下运行：

```shell
docker compose -p zhenxing_submission run --rm --no-deps init-data
```

该命令不会重置完整环境。遇到拒绝时先检查日志和项目归属，不要清库或删除标记来绕过保护。

## 4. 等待知识服务就绪

知识Worker首次启动时导入代码中的公开语料并创建索引任务，已有管理员修订不会被启动流程覆盖。后续升级语料时应在知识管理中核对新文档与索引状态，不能仅靠重启假定所有修订已经重新索引。Embedding首次下载较慢，页面能打开不表示向量检索已可用。

Windows PowerShell：

```powershell
Invoke-RestMethod http://127.0.0.1:18965/api/v2/health/ready
Invoke-RestMethod http://127.0.0.1:18193/health
```

Linux / macOS：

```sh
curl --fail http://127.0.0.1:18965/api/v2/health/ready
curl --fail http://127.0.0.1:18193/health
```

检查三层状态：

1. API健康返回`status: ready`，数据库和业务Worker可用。
2. Embedding返回`status: READY`、384维及已登记的模型版本。
3. 用`admin`登录后台的知识管理页，确认索引`index_state: READY`，有效内容片段均有当前版本向量。

本机Embedding使用模型文件集合的SHA-256作为`model_revision`。它应与发布配置及模型缓存manifest相符。该值不是模型名称，也不是任意填写的Hugging Face提交号。出现版本不符时先核对下载产物和缓存来源，不通过删除校验或随意改哈希来继续运行。

知识Worker受Embedding健康检查约束，向量网关还会在处理每批请求时检查模型、384维、token预算和固定artifact revision。版本不符的向量不能被激活为有效索引。检查失败后先修正下载或配置问题，再通过知识管理页重试失败的索引任务。

### 对话与图片模型分别核对

本版Compose将对话模型设为`deepseek-v4-pro`。图片提取在`vision_gateway.py`中固定请求`deepseek-flash`，使用电脑端的DeepSeek凭据；修改对话模型配置不会自动改变图片模块。

先验证纯文字查询。需要展示图片功能时，再用一张不含敏感信息的图片核对上传、云端提取、字段校验与用户确认。若图片接口或模型权限不可用，应保留明确失败状态，不能把文字模型健康当作图片识别成功。原图经过服务端重编码后仍会发往外部视觉API，正式数据接入前需完成准入确认。

## 5. 登录并核对数据

打开`http://127.0.0.1:18965/#/workspace`。

- 优先打开本机`app/var/private/首次登录.txt`，复制对应账户的完整初始口令。
- 客户用户名见[样例数据](样例数据.md)。密码规则为“用户名 + `.env`中的`ZX_INITIAL_CUSTOMER_SUFFIX`”，拼接时不加空格。
- 管理员用户名为`admin`，使用文件中的单独管理员口令，与客户后缀规则不同。
- 先查看用户资料，使用当前环境的卡号和联系人进行对话，不复制其他环境的完整卡号。
- 按[首次验收清单](首次验收清单.md)核对查询、确认、入账和连续追问。新环境的历史账单与产品持仓已经由初始化创建，不需要导入开发机数据库。

首次初始化的卡号和内部对象编号由本环境生成。固定日期与seed便于复现业务分布，不保证UUID或完整卡号逐字节一致。

## 6. 日常启停与更新

```shell
docker compose -p zhenxing_submission stop
docker compose -p zhenxing_submission start
docker compose -p zhenxing_submission restart api worker
```

`stop`与`start`保留数据卷。修改环境变量后应使用`up -d`重新创建容器，`restart`不会重新读取Compose环境配置。

更新代码前先备份业务库、知识库、附件和本地配置。保持项目名与数据卷不变，再构建并运行`up -d`。不要把新环境初始化当作升级或重置工具。不要在未知付款结果存在时删除任务或数据卷。

## 7. 运行日志与排错

```shell
docker compose -p zhenxing_submission logs --tail=80 api worker
docker compose -p zhenxing_submission logs --tail=80 embedding knowledge-worker
```

日志只用于本机诊断，分享前移除客户标识、凭据和上传材料。模型401/403、402、429以及Embedding下载或版本错误的处理见[排错](排错.md)。

移动连接按[手机连接](手机连接.md)显式开启私网网关。数据库不需要向手机开放。对公网提供服务前，还需独立认证、HTTPS、管理员访问隔离、模型数据准入和外部渠道验收。
